# Army Men II 踩坑清单

> 2 代汉化期间真实踩过的坑，按**代价**排序（越贵越靠前）。
> 每条都写了：现象 → 根因 → 修法 → 可移植的教训。
>
> 1 代的坑另见 [`02-pitfalls.md`](02-pitfalls.md)，两者可交叉参考。

## 坑 1：自绘裁剪 vs 转调游戏函数（代价最高）

**现象**：对话框文字渐显时花屏，全显示后正常。

**根因**：我自己实现了三层矩形求交 + 硬编码 640×480 做裁剪，
而原版是调用游戏自己的 `sub_42E220`。差异在于：

```c
// 原版
if (!rect(desc, &rcSrc2, &x, &y, out)) return 0;   // rcSrc2 为 0 矩形时裁光
```

`rcSrc2` 全 0 时原版**什么都不画**；我把它当"未设定"而忽略 → 照画 →
字形写到本该被裁掉的区域 → 越界出表面。

**修法**：改为转调 `sub_42E220`，与官方逐字对应。

> ★ **教训**：能转调就转调。本项目在"自行复刻游戏逻辑"上连摔 3 次。
> 复刻的每一个边界条件（`>=` 还是 `>`、0 矩形怎么算）都是出错面。

## 坑 2：漏 hook 文本测量函数

**现象**：任务简报窗口花屏，**且退出对话框也花屏**。

**根因**：英文版把"测量字符串宽度"做成独立函数 `sub_446E00`，
它对**每个字节**都查 ASCII 宽度表：

```c
result += *(WORD*)(atlas + offs[262*font + c] + 2) - 3;
```

汉字是双字节，首字节（如 `0xBF`）去查表 → **越出 ASCII 区间** →
取到别的数据 → 宽度算成垃圾。

调用点先算宽度、**再拿宽度当裁剪矩形**交给绘制函数。
宽度错 → 裁剪矩形错 → 文字被切碎。而 `rcSrc2` 是**全局**的，
所以污染会扩散到其它界面。

**修法**：hook `sub_446E00`，汉字按官方 `+= 15`。

> ★ **教训**：不画字但影响布局的函数最容易漏。
> 通用判据：**凡是消费字符串长度/宽度的函数，都要检查** ——
> 包括换行计算、居中计算、裁剪矩形设定。

## 坑 3：分支判定凭直觉加了保护

**现象**：持续花屏（首次进入界面正常）。

**根因**：判定写成了 `if (c > 0xA0 && s[1] != 0)` —— 多了后半句。

这些界面文字是**逐字节渐显**的，日志实证：

```
len=1   51 次  c4                  ← 孤立汉字首字节
len=3   32 次  b1 dc bf            ← 完整字 + 孤立首字节
len=24 304 次  b1 dc ... b0 b2     ← 完整串（正常）
```

每两步就产生一个奇数长度串。此时 `s[1] == 0`，条件不成立 →
**掉进 ASCII 分支** → 把汉字首字节当 ASCII 字符交给原版 →
原版查表越界 → 伪造 glyph 指针 → `sub_41C710` 把随机字节当 RLE 游程长度 →
**往屏幕刷大段颜色**。

官方条件是 `if (*v10 > 0xA0u)` —— **只看首字节**。

**修法**：判定只看首字节；孤立首字节走 CJK 分支但不绘制，
推进 1 字节防死循环，**绝不落到 ASCII 分支**。

> ★ **教训**：与官方的判定条件**逐字符对齐**。
> "凭直觉加的保护"往往造成相反后果。
> 实测：修复前 455 次泄漏，修复后 0 次；奇数长度帧占 39.6%。

## 坑 4：汉字步进用了点阵尺寸

**现象**：长串文字越走越偏，最终越界。

**根因**：官方汉字的**逻辑尺寸是 15**（`desc` 与步进都用 15），
而点阵实际只有 13×13。用 13 当步进 → 每字少走 2px → 累积偏移。

**修法**：`CJK_BOX = 15`（逻辑），`CJK_INK_W/H = 13`（点阵）。

> ★ **教训**：逻辑尺寸 ≠ 点阵尺寸。两个数都要照官方来。

---

## 坑 5：CENTER 渲染器的累加轴搞错

**现象**：居中文字位置错乱。

**根因**：我按"居中文字"的字面意思让它沿 x 推进，还多减了 3。
实际官方 `sub_446C50`：

```c
a4 = a1 - w/2;          // x 每字独立居中
result = v21 + h - 3;   // 累加器 v21 沿 **y** 推进
```

**修法**：区分 `axisY`；CENTER 的 x 每字独立算，y 累加。

> ★ **教训**：函数名是提示不是定义。看代码。

## 坑 6：stub 硬编码长度

**现象**：加了新 hook 后崩溃。

**根因**：`RendererBuildStubs` 里 `const int N = 5;` 是硬编码的。
三个渲染器入口是 `A1 imm32`（5 字节），但测量函数入口是
`mov ecx,[esp+8]; push esi; mov edx,ecx`（**7 字节**）。
按 5 复制会把第 6、7 字节（下一条指令的前半）也复制进 stub，
再 jmp 到 +7 → 从指令中间执行。

**修法**：`N = ins.len`（按各 hook 自己的 patchLen）。

> ★ **教训**：凡是"所有 hook 都一样"的假设，都要逐 hook 验证。

---

## 坑 7：patchLen 切在指令中间

**现象**：运行时看不出问题，但 stub 跳转会崩。

**根因**：曾用 `patchLen = 7`（想着"jmp 5 字节 + 2 字节 NOP 更整齐"），
而渲染器入口的指令起点是 `{0, 5, 8, ...}` —— **+7 不是边界**，
把 `sub esp,0x2c` 切成了两半。

**修法**：patchLen 必须逐 hook 用反汇编验证（`verify_stub_boundary.py`）。

> ★ **教训**：改函数入口前必查指令边界。

## 坑 8：校验器空转报绿（4 种失效方式）

本项目踩过 4 次，全部发生在校验器自己身上：

| 失效方式 | 表现 | 修法 |
|---|---|---|
| **白名单过滤** | `s in ("SIG_A","SIG_B")` → 新加的 `SIG_C` 被静默忽略，仍打印"全部通过" | 改前缀匹配 + 断言覆盖度 |
| **硬编码条目数** | `EXPECT` 写死 3 项 → 新增的第 4 项没查 | 从源码解析实际条目 |
| **累计到阈值就停** | 指令列表只有第一条，后续"是否边界"必然失败（**假红**） | 反汇编完整窗口再判断 |
| **解析正则不匹配** | 匹配 0 条，脚本"什么都没查"却报通过 | 断言"检查数 > 0" |

**要求**：
- 报出**实际检查的条目数**
- **断言覆盖度**（期望的类别必须都被查到）
- 空转即失败

> ★ **教训**：校验器要自证。它比被测代码更需要被怀疑。

## 坑 9："自动部署"只有 print 没有 copy

**现象**：每轮构建都打印"已自动部署"，但游戏目录里一直是旧 DLL。
白费一轮实机验证（而且旧 DLL 没有诊断日志，
我会误判成"诊断没生效"而不是"文件没换"）。

**根因**：脚本里那段只有 `print(...)`，没有 `shutil.copyfile`。

**修法**：
1. 真拷贝
2. 每个文件 **sha256 回读校验**（不只信 `copyfile` 调用成功）
3. 失败即非零退出

> ★ **教训**：与坑 8 同类 —— **声称成功但没做事**。
> 任何"已完成"的打印，都要有对应的验证。

---

## 坑 10：PE 时间戳让"是否需要部署"永远为真

**现象**：幂等性检查失效，每次构建都报"已更新"，
真正的改动被淹没在噪声里（这也是坑 9 没被早发现的原因）。

**根因**：PE 里 `TimeDateStamp` 每次链接都变。
逐字节对比两次构建：全文件仅 **4 字节**不同 ——
PE 头 `+8` 的 `TimeDateStamp`，以及它在 `.rdata` 里的**一份内联副本**
（文件偏移 `0x2E7F4` / RVA `0x2F5F4`）。

**修法**：比较前把这两处抹平（`_norm_pe_hash`）。

> ★ **教训**：先**逐字节定位**差异，再决定抹平什么 —— 不要猜有哪些易变字段。

---

## 坑 11：靠目视验证字形正确性

**现象**：一度误判"Hzk16 字形偏移公式错了"，白费一轮。

**根因**：判据是"汉字看着像不像字"。而 13×13 点阵里
**任何切片都像字** —— 我把噪声看成了工整字形。

**修法**：改用**不可混淆**的判据 —— GB2312 第 3 区的全角 ASCII
（`ＡＢＣＤＥＦ` / `０１２３`），目标是"认出是哪封信"而非"看着像字"。
并让测试**自证区分力**：全偏移扫描 202,940 个位置，
命中指纹的仅 **0.717%**。

**其它弱判据**（实测不可用）：

| 判据 | 问题 |
|---|---|
| "汉字看着像不像字" | 任何切片都像字 |
| "墨迹量落在 8..110" | 随便一段数据都满足 |
| "一/二/三 横线条数" | 有 **138** 个偏移值都能满足 |

> ★ **教训**：判据要不可混淆，且测试要能区分正误。

## 坑 12：把"推导"当成"已验证"

**现象**：一个子代理分析后主张"缺 `dataStart`，所有字都读错"，
推导过程看起来严谨，差点据此改掉正确的公式。

**根因**：它只看了静态公式形式，未意识到官方 `sub_426DB0` 里的 `base`
在**运行时已指向 `文件 + 0x694C`** —— `-9688` 正是为它预留的补偿量。

**判据**：用全角 ASCII 一验即知 —— 当前公式画出的是标准字母，
它主张的公式画出的是噪声。

> ★ **教训**：推导再漂亮也要**用可执行的判据验证**。
> "看起来合理"不是证据。

## 坑 13：在同一个症状上连续猜

**现象**：花屏这一个症状，耗了 **6 轮**。

**根因**：每轮都是"怀疑某处 → 改 → 请你实测"，
而缺少**决定性数据**。

**转折点**：加**有界诊断日志**（前 N 次 + 之后每 M 次记录），
把"实际字符串内容、坐标、裁剪框、表面指针"落盘。
拿到日志后，一眼就看出：

```
len=1  51 次  c4      ← 孤立汉字首字节
len=3  32 次  b1 dc bf
```

**修法**：先上加诊断，再定位。

> ★ **教训**：
> - 无法本地复现时，**先建可观测性**，不要连续猜
> - 日志要用**原始字节**（十六进制），不要只记"转换后的文本" ——
>   正是原始字节暴露了"孤立首字节"
> - 诊断要有界（限量防爆），但要覆盖前若干次（首次异常才有价值）

## 坑 14：日志中 `printf` 的 `%s` 遇到非法 GBK

**现象**：日志里中文显示为乱码（如"鑻辨枃"）。

**根因**：用 UTF-8 读取含 GBK 字节的日志。日志文件本身是 UTF-8，
但 `%s` 写入的是**原始 GBK 字节**（未转换）——
这对诊断反而**有用**（能看到真实字节），只是读取时要按 GBK 二次解码。

**修法**：读取时先按字节取，再尝试 GBK 解码；十六进制优先。

> ★ **教训**：诊断日志的编码要明确；能直接给十六进制就别给文本。

---

## 坑 15：`core.autocrlf=true` 破坏游戏资产

**现象**：仓库里的资产被改写，游戏按字节解析时崩溃。

**根因**：本机 `core.autocrlf=true`，Windows 检出时把 LF 改写成 CRLF。
对游戏按**字节**解析的资产就是逐字节损坏。

**修法**：`.gitattributes` 里把资产一律标 `-text`。

2 代补充：实测 `.wav` 目前**未被改写**（git 靠"内容像二进制就跳过"
的启发式兜底），但那是**偶然保护**不是声明。已显式补上
`*.wav` / `*.ani` / `*.ast` / `*.axs` / `*.sdb` / `*.vdf` / `*.isu` / `*.ico`。

> ★ **教训**：不要依赖启发式。显式声明。

**提交前必做**：全量校验 blob 与工作区文件一致。

```powershell
# 逐文件比对（1795 个文件实测通过）
git diff --cached --name-only | ForEach-Object {
  $blob = git hash-object -- $_
  $staged = (git ls-files -s -- $_ | ForEach-Object { ($_ -split '\s+')[1] })
  if ($blob -ne $staged) { "不一致: $_" }
}
```
