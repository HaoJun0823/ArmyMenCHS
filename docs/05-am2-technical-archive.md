# Army Men II 汉化技术档案（可复用于 3 / 4 代）

> 本文记录**已实测验证**的事实。每条都标注了验证方式，未验证的明确标为 ❓。
> 3 / 4 代引擎与 2 代几乎一致（不同于 1→2 代的巨大差异），故本文大部分内容
> 可直接迁移。移植步骤见 [`05-am2-porting-guide.md`](05-am2-porting-guide.md)。

---

## 0. 一句话总结

2 代引擎**自带点阵字体、不走 GDI**，文本渲染由**三个独立函数**完成；
汉化的本质是：

1. 用 ASI 挂钩这 3 个渲染器 + 1 个测量函数
2. 汉字走 `Hzk16` 点阵自绘，ASCII 原样转调原函数
3. 译文从 INI 写入 `.rdata` 字符串槽

**不改 exe**（硬约束，见 §7）。

## 2. 文字渲染：三个绘制函数 + 一个测量函数

### 2.1 为什么是"三个"

引擎里文字**不是**一个函数画完的。只挂一个会导致其它路径的文字完全不显示
（字符串确实被我们改成了 GBK，但负责画它的那个函数还是 ASCII 实现，
遇 `>0xA0` 的字节查表越界 → 什么都不画）。

| 函数 | RVA | 参数量 | 用途 | 裁剪矩形 | 累加轴 |
|---|---|---|---|---|---|
| `sub_446930` | `0x46930` | 6 | 左对齐（面板文字） | ❌ 无 | x |
| `sub_446AB0` | `0x46AB0` | 9 | 对话框（退出确认等） | ✅ 有 | x |
| `sub_446C50` | `0x46C50` | 9 | 居中文字 | ✅ 有 | **y** |

中文版对应：`sub_446B00`（LEFT）/ `sub_446D40`（DIALOG）/ `sub_446FB0`（CENTER）。

> ★ CENTER 的累加轴是 **y**（官方 `v21 += h - 3`），不是 x。
> 我按"居中文字"的字面意思沿 x 推进过，是错的。
> 它的 x 每字独立居中（`a4 = a1 - w/2`）。

### 2.2 第四个：文本测量（最容易漏）

| 函数 | RVA | 原型 |
|---|---|---|
| `sub_446E00` | `0x46E00` | `int f(const char* str, int font)` |

英文版实现对**每个字节**都查 ASCII 宽度表：

```c
result += *(WORD*)(atlas + offs[262*font + c] + 2) - 3;
```

汉字是双字节，首字节（如 `0xBF`）会去查 **ASCII 表区间之外**的位置 ——
取到别的字符的数据，宽度算成垃圾。

**为什么漏了它会花屏**：调用点 `sub_419AC0`（任务简报窗口）先调它算宽度，
**再拿这个宽度当裁剪矩形**交给绘制函数。宽度错 → 裁剪矩形错 →
文字被切碎错位。而 `rcSrc2` 是全局的，一旦被污染，**退出对话框也跟着花屏**。

中文版对应 `sub_446A70`：

```c
if (c >= 0xA0u) result += 15;      // 汉字固定 15，不查 ASCII 表
```

### 2.3 官方中文版的完整逐句（LEFT 为例）

```c
int sub_446B00(int x, int y, char* str, int font, int a5, int color)
{
    if (!dword_4FDB68) return 0;              // ① 表面锁标志，为 0 一字不画
    for (each char) {
        if (c == '^' && 还有下一字节) { color = 下一字节; continue; }   // ② 颜色转义
        glyph = dword_6596BC[131*font] + word_6594BC[262*font + c];
        if ((BYTE)c > 0xA0) { w = 15; h = 15; }        // ③ 汉字逻辑尺寸恒为 15
        else                { w = glyph[0]; h = glyph[1]; }
        desc = {0, 0, w, h};
        if (!rect(desc, &rcSrc2, &x, &y, out)) return 0;   // ④ 全局裁剪
        if (locked == primary) { x += rc.left; y += rc.top; }  // ⑤ 裁剪**之后**加偏移
        if (c > 0xA0) {
            p = 查点阵(c);                              // ⑥ Hzk16
            for (i = 0; i < 13; i++)                    //    只画 13x13
                for (j = 0; j < 13; j++)
                    if (bit) surface[i + pitch*(j+y) + x] = color;
        } else blit(...);                               // ⑦ ASCII 照旧
        x += w;                                         // ⑧ 步进 = w（汉字 15）
    }
}
```

**③ 与 ⑧ 是最关键的两个数**：汉字逻辑尺寸 15，而点阵只有 13×13。
用 13 当步进 → 每字少走 2px → 长串累积偏移 → 越界写出表面 → 花屏。

## 3. 共享数据表与全局量（绝对 VA）

| 名称 | VA | 结构 | 说明 |
|---|---|---|---|
| `word_6598D4` | `0x6598D4` | `WORD[262*font + c]` | 字形在 atlas 内的**字节偏移** |
| `word_659914` | `0x659914` | `WORD[262*font + c]` | 字符**步进宽度** |
| `dword_659AD4` | `0x659AD4` | `DWORD[131*font]` | ★ 其**内容**是 malloc 堆指针，不是 RVA |
| `rcSrc2` | `0x485310` | `RECT` | 全局裁剪矩形 |
| `rc` | `0x485330` | `RECT` | 后备缓冲在主表面中的**原点偏移** |
| `dword_507128` | `0x507128` | `DWORD` | 当前锁定的表面 |
| `dword_502AD4` | `0x502AD4` | `DWORD` | 主表面 |
| `dword_4FDF80` | `0x4FDF80` | `DWORD` | 表面锁标志（0 = 未锁） |
| `nWidth` / `nHeight` | `0x4852D8` / `0x4852DC` | `int` | 显示区尺寸（静态初值 640 / 480） |
| `dword_4FE1A8` | `0x4FE1A8` | `BYTE*` | 目标像素缓冲（**解锁时被清零**） |
| `dword_502AD0` | `0x502AD0` | `int` | 行距 pitch（**解锁时被清零**） |

中文版地址不同（见 `target.cpp` 的 `ArmyMenII-CHS` 档位）。

### 3.1 三个原语函数

| 函数 | VA | 作用 |
|---|---|---|
| `sub_41C710` | `0x41C710` | 字形 blit：`(x, y, glyph, r0..r3, color)` |
| `sub_42E220` | `0x42E220` | 矩形裁剪/定位，**就地修改 x/y** |
| `sub_41B9A0` / `sub_41BA40` | `0x41B9A0` / `0x41BA40` | 锁/解锁表面 |

★ **`sub_41BA40`（解锁）会把 `dword_4FE1A8` 与 `dword_502AD0` 清零**。
对话框"文字渐显"跨帧、跨多次锁/解锁，所以**每次落笔前都要重新读这两个值**，
不能在函数入口读一次用到底。

## 4. 中文字库 Hzk16

| 项 | 值 |
|---|---|
| 大小 | 202,966 B |
| 魔数 | `RSE\x1a`（小端 DWORD = `0x1A455352`） |
| 字形 | 13 × 13，2 字节/行，26 字节/字形 |
| 字形数 | 6768（文件头 `0x52` 处 WORD） |
| 数据起点 | `0x694C`（文件头 `0x48` 处 DWORD） |
| 字体名 | `宋体`（`0x20` 处 GBK 串） |
| GBK 范围 | `0xA1B0`–`0xFEF7` |

### 4.1 字形偏移公式（★ 易误判）

官方 `sub_426DB0`：

```c
v2 = height * ((width + 7) >> 3) * (trail + 94*lead - 15295) - 9688;
if (v2 < 0) v2 += 9776;
return base + v2;
```

其中 **`base` 在运行时已指向 `文件 + 0x694C`**，`-9688` 正是为它预留的补偿。
所以在**文件层面**的等价形式是：

```
idx = trail + 94*lead - 15295
off = 26*idx - 9688          // idx < 373 时 +9776
```

### 4.2 判据必须"不可混淆"（两次误判的教训）

同一个问题被误判过两次：

| 轮次 | 判据 | 结果 |
|---|---|---|
| 1 | 目视"中/文"像不像字 | 把**噪声**看成工整字形 → 误判"公式正确" |
| 2 | 推导"缺 dataStart，所有字读错" | 未意识到 `base` 的运行时语义 → 误判"公式错误" |

**弱判据**（不可用）：
- "汉字看着像不像字" —— 13×13 里任何切片都像字
- "墨迹量落在 8..110" —— 随便一段数据都能满足
- "一/二/三 横线条数" —— 实测有 **138** 个偏移值都能满足

**强判据**（已固化进 `Tools/ci/verify_hzk_offset.py`）：
用 GB2312 第 3 区的**全角 ASCII**（`ＡＢＣＤＥＦ` = `0xA3C1..`，`０１２３` = `0xA3B0..`）。
这些字形与半角字母**形状完全一致**，目标是"认出是哪封信"而非"看着像字"。
错位读取要恰好拼出 ABCDEF0123 —— 概率为零。

并且该测试**自证区分力**：全偏移扫描 202,940 个位置，命中指纹的仅
**0.717%**，证明判据真能区分正误（不是又一个空转的校验器）。

## 5. 内存字符串补丁

### 5.1 表格式

译文外置为 INI，键为 **RVA**（不是 VA）：

```ini
0x8b74c=Are you sure you want to quit?|你确实想退出吗？
```

DLL 侧的**安全闸门**：写入前比对"内存现状 == 英文原文"，不一致就拒绝写入。
这能挡掉"RVA 算错"导致改坏无关数据。

### 5.2 容量约束

槽容量 `cap = len(英文原文) + 1`（含 NUL）。
中文译文（GBK）不得超出，否则会覆盖相邻字符串。

> 例：`Jeeps` 容量 6 字节，`吉普车` 需 7 字节 → 超限。
> 解法是改用更短译名（`吉普`）或计入例外表。

### 5.3 字符串表布局（实测）

- 表项步长 `0x24`
- 首项名称指针 `0x865D8`（`POWER-UPS`）
- 末项 `0x86BC0`
- 中文版对应表项的 RVA = Steam 版 − `0x78`

## 6. 注入方式

### 6.1 为什么选 `dinput.dll`

用 Ultimate ASI Loader (UAL) 9.0.0 做代理。选择依据是**导入表**：

| 候选 | 结果 |
|---|---|
| `dinput.dll` | ✅ AM2/TIS **按名字**导入 `DirectInputCreateA` → 可用 |
| `dsound.dll` | ❌ 按**序号**导入 → 代理无法解析函数名 → 不可用 |

用 `Tools/exe_scan/list_imports.py` 确认候选 DLL 与导入方式。

### 6.2 UAL 的 `update\` 机制

- UTF-16 字符串 `update\` @ `0xa6780`
- 配套 `global.ini` 的 `overloadfromfolder`
- **目录存在即生效，无需 `global.ini`**（1 代已实机验证）

### 6.3 约束

- UAL 只扫 `scripts\*.asi`；把 `.dll` 丢进 `scripts\` 会被**静默忽略**
- 编译产物必须是 32 位（`/MACHINE:X86`）

## 7. 硬约束：不改 exe

**理由**：

1. Steam 更新会让补丁失效，且难以回滚
2. 本项目的"中文函数重建"要兼容后续作品（3/4 代引擎同源），
   改 exe 等于给每一代维护一份二进制补丁
3. 无法通过校验

**代价**：需要找 IAT 表项、构造 ASI 环境、所有改动走运行时内存。

**结论**：收益远大于代价。3/4 代沿用。

## 8. hook 安装的三个必须

### 8.1 patchLen 必须落在**指令边界**

三个渲染器入口是：

```
+0  mov eax, [0x4fdf80]    A1 80 DF 4F 00    5 字节
+5  sub esp, 0x2c          83 EC 2C          3 字节
```

指令起点 `{0, 5, 8, ...}`，**+7 不是边界**。
用 7 会把 `sub esp,0x2c` 切成两半：运行时因整段被 jmp 跳过而看不出问题，
但 stub 会复制半条指令 → 从中间执行 → 崩溃。

测量函数入口是：

```
+0  mov ecx, [esp+8]       8B 4C 24 08       4 字节
+4  push esi               56                1 字节
+5  mov edx, ecx           8B D1             2 字节
```

累计 7 才是边界。**每个 hook 的 patchLen 必须单独验证**，
不能全局用一个值（`Tools/ci/verify_stub_boundary.py` 会逐 hook 反汇编确认）。

### 8.2 stub 必须按实际 patchLen 复制

stub 布局：`[原始 N 字节][jmp rel32 -> 原函数+N]`。
这里 **N 必须等于该 hook 的 patchLen**。硬编码 5 会在 patchLen=7 时复制到
下一条指令的前半，跳转后从指令中间执行 → 崩溃。

### 8.3 分支判定要与官方一致

官方是 `if (c > 0xA0)` —— **只看首字节，不要求尾字节存在**。

若写成 `if (c > 0xA0 && s[1] != 0)`，当串以**孤立汉字首字节**结尾时
（见 §9）会掉进 ASCII 分支 → 越界查表 → 花屏。

## 9. 逐字节渐显：最隐蔽的杀手

这些界面的文字是**逐字节揭示**的动画。日志实证（`避开黄军突击队，前进至安`）：

```
len=1   51 次  c4                  ← 孤立汉字首字节
len=3   32 次  b1 dc bf            ← 完整字 + 孤立首字节
len=5   36 次  b1 dc bf aa bb      ← ...
len=24 304 次  b1 dc ... b0 b2     ← 完整串（这一帧正常）
```

即**每两步就产生一个奇数长度串**，末尾是孤立的汉字首字节
（实测 39.6% 的绘制帧是这种）。

处理要求：
- 分支判定**只看首字节**（§8.3）
- 孤立首字节走 CJK 分支但**不绘制**，只推进 1 字节防死循环
- **绝不落到 ASCII 分支**（那正是花屏根因）

## 10. 代码补丁

除字符串外，还有一类"改代码字节"的补丁，例如解锁被封锁的多人模式：

```
Offset: 4D8FE: EB 55 -> 74 55
（特征串 03 00 00 00 EB 55）
```

每条补丁都要做**多字节原文校验**，不符即跳过（`Tools/ci/verify_codepatch.py`）。
